# 実例：キャラクターの自発的な散歩便りシステムへの適用

キャラクターが「散歩に行きたい度合い（欲求値）」を持ち、満ちると自発的に散歩へ出て、実在の場所とストリートビューの景色をもとに便りを送るシステムに、この2層化を適用した例。

## 構成

- 第1層：hook（5分間隔）が時計スクリプトを回し、時刻帯フェーズ・眠気・行動ごとの欲求値を JSON 状態で進める。何も起きなければ silent で終わり、トークン消費ゼロ。
- 第2層：発火時のみエージェントが起き、手順書（行き先選定・ストリートビュー観察・文面作成・状態への書き戻し）に従って行動する。
- 文脈同期：cron（1時間ごと）が会話の話題・天気・ユーザーの睡眠推定を状態の `context` へ書く。時計はそれを読むだけ。
- 状態の分け方：共有するのはフェーズ・眠気・気分だけ。欲求値は行動（散歩／挨拶／話しかけ等）のモジュールごとに独立した箱で持つ。

## 検算で起きたこと

- 当初案の加算量（base 10／5分）のままシミュレーション（4日分・複数シード）すると、出発が1日8〜9回に膨れた。稼働帯が約16.5時間と長いため。
- base を 4.0／5分まで下げて出発4〜6回／日に収め、便り換算で目標帯に入れた。**頻度は勘ではなくシミュレーションで決める**のが要点。
- 影モードでは消費を模擬しないと欲求が減らず、発火頻度が過大に見積もられる。模擬消費（満足度0.6固定）を入れて現実に寄せた。

## 検証の順序（実際に踏んだ手順）

1. hook 登録 → dry_run で silent を確認。
2. 状態の複製を live モードにし、欲求値を発火帯へセットして時計を手で実行 → decision=wake、payload、処理中フラグの立ち方まで確認。
3. 影モードで本番設置し、旧仕組み（30分間隔のエージェント cron 群）は並走のまま残した。
4. 影ログを1日見てから live 切替と旧 cron の無効化を同時に行う計画とした。
